# Internationalization

Official locales: **English (`en`)** and **Portuguese (Brazil) (`pt-BR`)**. The preference persisted in SQLite is `system`, `en` or `pt-BR`.

## Selection and persistence

`system` is the default for new databases and upgrades from version 0.1. On desktop, `sys-locale` reports the system locale; in frontend development, `navigator.language` is used. Locales starting with `pt` use `pt-BR`; all others use `en`. A persisted manual selection takes precedence over the system on subsequent launches.

**Settings → General → Language** / **Configurações → Geral → Idioma** applies the change without restarting. The `react-i18next` context updates components and the shell receives `set_menu_language`, rebuilding native menus with the same catalogs. Appearance has its own independent preference.

## Files

```text
app/src/i18n/index.ts              inicialização, detecção, formatos e mensagens
app/src/i18n/locales/en.json       catálogo inglês
app/src/i18n/locales/pt-BR.json    catálogo português
```

The file listing above retains the original annotations; it identifies initialization/detection/formatting/messages and the English and Portuguese catalogs, respectively.

Catalogs are flat objects with `keySeparator=false` and `nsSeparator=false`. New semantic keys follow groups such as `scientific.*`, `references.*`, `content.*`, `graph.*`, `general.*`, `menus.*`, `errors.*`. Keys under `copy.*` identify text migrated from 0.1; the stable suffix prevents collisions between similar text. New hashed keys are unnecessary: prefer semantic names for future changes.

`labels.*` translates only known canonical codes for navigation, stages, status and categories. `legacy.*` adapts UI messages already persisted by previous versions; unknown technical messages receive a useful generic message, with details kept in the log.

## Add a string

1. Add the same key to both JSON files.
2. Use `const {t}=useTranslation()` in the component and `t('grupo.chave')`.
3. Use named interpolation: `t('content.pageRange', {start, end})`.
4. Do not compose translated sentences from fragments when one complete key can express the text.
5. For internal codes, keep the code in state and translate only its presentation.

Translation also covers tooltips, accessible labels, placeholders, empty states and menus. Do not add new text directly to JSX or UI attributes. The static test covers the main components. New keys must exist in both catalogs; a parity test checks this.

## Scientific content is not translated

Never pass titles, abstracts, author names, journals, original headings, raw citations, source excerpts or user notes through `t()`/`label()`. The UI translates only the canonical label, for example `methods → Methods / Métodos`. The **Materials and Methods** heading received from the document stays exactly in the source language. The expanded PETRUS name remains in English as part of its institutional identity.

## Formats and fallback

Dates use `Intl.DateTimeFormat` through `toLocaleDateString` with the active locale. Counts use `Intl.NumberFormat` and the i18next numeric formatter; identifiers, DOIs, publication years and page numbers are not reformatted as local quantities.

`fallbackLng='en'` resolves a missing Portuguese translation through the English catalog. A completely unknown key produces **Text unavailable / Texto indisponível**, without breaking the interface. Development emits a `[PETRUS i18n]` warning; the product bundle neither saves translations nor communicates over the network. The test checks detection, manual selection, fallback, persistence, immediate updates, formatting and the absence of primary copy outside the catalogs.

## Add a language

Create another JSON file with the same keys and register the resource and `supportedLngs` in the initializer. Update the central `preferredLocale` policy, setting validation in the engine, native-menu catalog selection and the General selector. Add persistence, formatting and parity tests. Do not scatter locale conditionals across components.
